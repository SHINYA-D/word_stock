# オンライン・オフライン同期 振る舞い仕様書

## 1. 機能概要

ローカル（SQLite）とリモート（現在は Firestore）の間で、フォルダ・単語・成績・設定を同期する。
画面は持たない。読み取りは常にローカルから行い、変更はキュー（`sync_queue`）を通してリモートへ送る。
各データの登録・編集・削除の契約は、同じフォルダの Repository ごとの仕様書に書く。

| 仕様書 | 接頭辞 |
|-------|-------|
| `folder_repository.md`（フォルダ） | FLD |
| `word_repository.md`（単語） | WRD |
| `flashcard_result_repository.md`（成績） | FRS |
| `settings_repository.md`（設定） | STG |

## 2. データ定義

### 2.1 ローカルの各データに共通の項目

| 項目 | 型 | 説明 |
|------|----|------|
| updatedAt | DateTime（ローカルには UTC の ISO8601 文字列で保存） | 最後に変更した時刻（変更した端末の時計） |
| deletedAt | DateTime? | 削除した時刻。未削除なら null。設定は持たない |
| syncStatus | `pending` / `synced` | キューに未送信の変更があるか |

### 2.2 リモートの各データに共通の項目

| 項目 | 型 | 説明 |
|------|----|------|
| updatedAt | 日時 | ローカルの updatedAt と同じ時刻 |
| deletedAt | 日時 / null | ローカルの deletedAt と同じ時刻 |
| サーバー受付時刻 | 日時 | リモートが受け取った時刻（サーバーの時計） |

### 2.3 キューの項目

| 項目 | 説明 |
|------|------|
| 順番 | 積んだ順（自動採番） |
| userId | 変更したユーザー |
| テーブル名・レコード id | 変更したデータ（単語は親フォルダの id も持つ） |

### 2.4 入力ルール

該当なし（ユーザーの入力を受け付けない）。

## 5. 同期の契約

特に書かない限り、次を前提とする。

- ユーザー U がログイン中で、オンラインである
- 「ローカル」「リモート」の中身はすべて U のデータ
- 「新しい」「古い」は updatedAt の前後で比べる

観測点は、ローカルの行（項目の値・syncStatus）、Repository の取得メソッドの戻り値、リモートのドキュメント（存在と項目の値）、キューの件数と並び、取得の基準（ユーザーごとにローカルに記録した値）、リモートへの呼び出しの順番とする。

## 7. 対象外

- **Firestore SDK のオフライン機能（persistence）を無効にしていること**: 起動時の設定値で、単体テストでは観測できないため（コードレビューで確認する）
- **ログイン後、取得が終わるまでホーム画面に進まないこと**: 画面遷移なので、ログイン画面の仕様書で定める。UseCase が取得を終えてから戻ること（SYN-L01・L04）までをこの仕様書で扱う
- **同期の失敗を画面に表示しないこと**: 同期には画面がないため、表示を観測する対象がない。ログアウトしないこと（SYN-T16）だけを扱う
- **成績の編集を取得・送信したとき**: 成績は編集しないため（概要 §データの持ち方）
- **成績の送信で、リモートの成績がローカルと同じか新しい場合**: 成績の id は登録のたびに新しく作られ、編集もしないため、登録を送る時点でリモートに同じ成績があることはない。削除（SYN-S27）も、配下を削除したフォルダの削除より新しい変更がリモートの成績に入ることがないため
- **設定の削除を取得・送信したとき**: 設定は削除しないため
- **ネットワークにつながっているがサーバーに届かない場合**: 送信・取得のリモートの失敗（SYN-S14・T14・P32）と同じ結果になるため、個別の項目を作らない
- **`NotFoundFailure` / `UnknownFailure` / `NetworkFailure`（送信・取得）**: 同期は Failure を画面に返さない。リモートの失敗はすべて「失敗した」として同じ扱い（SYN-S14・T14・P32）になるため、種類ごとの項目を作らない。`AuthFailure` に当たる失敗だけは、ログアウトしないことを SYN-T16 で確認する
- **論理削除した行の掃除（物理削除）**: 今回は作らないため（概要 §目的と前提）
- **ログアウト時に送信とログアウトを呼ぶ順番（`SignOutUseCase`）**: 送信してからログアウトするだけで、独自の分岐がないため
- **ログアウトした端末に残るデータの容量・プライバシー**: 読み取り・送信はログイン中のユーザーに絞る（SYN-O07）ため、振る舞いとしては観測する対象がない
- **Firestore に依存する処理をリモートとの読み書きの部分に閉じ込めること**: コードの構造の決まりで、振る舞いとして観測できないため（アーキテクチャのレビューで確認する）
- **SQLite のトランザクションを開いたままリモートと通信しないこと**: 実装の制約で、単体テストの観測点がないため（コードレビューで確認する）
- **送信時の「比べてから書き込むまでの割り込み」を防ぐこと**: リモート（Firestore のトランザクション）の保証で、単体テストでは再現できないため
