# オンライン・オフライン同期 概要設計書

## 目的と前提

- ネットワークがない場所でも、ログイン後の機能（フォルダ・単語・成績・設定の閲覧と登録・編集・削除）をそのまま使えるようにする。
- 複数の端末で同じアカウントを使ったとき、どの端末でも最終的に同じデータになるようにする。
- リモート（サーバー側の保存先）は現在 Firebase（Firestore）だが、将来 Firebase をやめる可能性がある。
  そのため、オフライン対応は Firestore SDK のオフライン機能に頼らず、**端末の SQLite と同期キュー（`sync_queue`）で自前で行う**。
  Firestore SDK のオフライン機能（persistence）は無効にする。
- リモートが Firestore 以外に変わっても、この設計書の振る舞いは変えない。Firestore に依存する処理は、リモートとの読み書きを担当する部分だけに閉じ込める。

### 対象外

- ログイン・新規登録・パスワードリセットは、オフラインでは使えない（Firebase Auth が必要なため）。
- 同期の状態（未送信の件数・同期中など）を画面に表示する機能は、今回は作らない。
- 論理削除した行の掃除（物理削除）は、今回は作らない（将来対応）。

## 用語

| 用語 | 意味 |
|-----|------|
| ローカル | 端末の SQLite |
| リモート | サーバー側の保存先（現在は Firestore） |
| キュー | リモートにまだ送っていない変更の一覧（`sync_queue` テーブル） |
| 取得 | リモートの変更をローカルに反映すること |
| 送信 | キューに溜まった変更をリモートに反映すること |
| 同期処理 | 「取得」をしてから「送信」をする一連の処理 |
| updatedAt | そのデータを最後に変更した時刻。変更した端末の時計で付ける。競合の判定に使う |
| サーバー受付時刻 | リモートがそのデータを受け取った時刻。サーバーの時計で付ける。差分取得の基準に使う |

## 基本方針

| 場面 | 動き |
|-----|------|
| 読み取り | オンライン・オフラインに関係なく、**常にローカルだけから読む**。画面はオンラインかどうかを意識しない |
| 登録・編集・削除（オンライン） | ローカルに保存し、同時にキューに積む。保存が終わったらすぐに送信し、リモートにも登録する |
| 登録・編集・削除（オフライン） | ローカルに保存し、同時にキューに積む。送信はしない |
| 他の端末での変更 | 取得のきっかけ（後述）ごとにリモートから変更を取得し、ローカルに反映する |
| オンライン復帰 | まずリモートから変更を取得し、その後でキューを送信する |
| 同じデータを両方で変更していた場合 | **updatedAt が新しい方を正とする**（削除も「変更」の一つとして同じルールで比べる） |

- 登録・編集・削除は、オンラインでもオフラインでも**同じ流れ**（ローカルに保存 → キューに積む → オンラインなら送信）にする。
  オンライン時に送信が失敗しても、変更はキューに残り、次のきっかけで再送する。
- 登録・編集・削除の結果（成功・失敗）は、ローカルへの保存の結果で決める。送信の成否は、画面の操作結果に影響させない。
- ローカルへの保存とキューへの登録は、**必ず同じトランザクションで行う**（片方だけ成功する状態を作らない）。
- 送信・取得の途中で、SQLite のトランザクションを開いたままリモートと通信しない。

## データの持ち方

### 各データに共通で持つ項目

フォルダ・単語・成績・設定の各データは、ローカルとリモートの両方で次の項目を持つ。

| 項目 | ローカル | リモート | 説明 |
|-----|---------|---------|------|
| updatedAt | ○ | ○ | 最後に変更した時刻（変更した端末の時計）。競合の判定に使う |
| deletedAt | ○ | ○ | 削除した時刻。削除されていなければ空（null） |
| サーバー受付時刻 | — | ○ | リモートが受け取った時刻（サーバーの時計）。差分取得の基準に使う |
| 同期状態（syncStatus） | ○ | — | `pending`（キューに未送信の変更がある）/ `synced`（未送信の変更がない） |

- 設定はユーザーごとに1件だけで、削除はしない（deletedAt は持たない）。
- 成績は登録だけで、編集はしない。削除はフォルダの削除に連動するときだけ行う。

### 論理削除

- 削除は、行を消さずに deletedAt と updatedAt に削除した時刻を入れる（論理削除）。リモートにも同じように deletedAt を入れたデータを送る。
- 読み取りでは、削除済み（deletedAt が入っている）のデータは返さない。
- 削除済みのデータは、編集・削除の対象として扱わない（存在しないものとして扱う）。
- 削除も updatedAt を持つので、編集と削除がぶつかったときも updatedAt で決着をつける。
  たとえば、この端末で削除した後に、別の端末でそれより新しい編集があった場合は、編集が正になり、データは復活する。

### キュー

- キューには「どのユーザーの、どのデータ（テーブルと id）に変更があったか」と、積んだ順番だけを持つ。変更の中身は持たない。
- 送信するときは、その時点のローカルの最新の行をそのまま送る。
  そのため、同じデータを何回変更しても、送る内容は最新の1つになる。
- 日時はどの項目も日時として送る。文字列の内容から日時かどうかを推測して変換することはしない（単語に「2024-01-01」と入力しても文字列のまま送る）。

### 日時の扱い

- 画面・UseCase・Repository では、日時は常に `DateTime` として扱う。
- ローカルには UTC の ISO8601 文字列で保存する。文字列と `DateTime` の変換は、SQLite を扱う層（LocalDataSource）だけで行う。
- リモートには日時型で保存する。

## 取得（リモート → ローカル）

- 取得は、前回の取得以降に**サーバーが受け付けた**変更だけを対象にする（サーバー受付時刻で絞る）。
  端末ごとの時計のずれや、オフラインで変更されて後から送られたデータがあっても、取りこぼさないようにするため。
- 取得の基準（どこまで取得したか）はユーザーごとにローカルに記録する。記録がないとき（初めてのログイン・再インストール後など）は、すべてのデータを取得する。
- 取得の途中で失敗した場合は、取得の基準を進めない。次の取得で、同じ範囲をもう一度取得する（同じデータを2回反映しても結果は変わらない）。
- 取得した1件ごとに、ローカルの状態に応じて次のように反映する。

| ローカルの状態 | リモートの状態 | 反映のしかた |
|--------------|--------------|------------|
| 存在しない | 削除されていない | ローカルに追加する（synced） |
| 存在しない | 削除済み | 何もしない（ローカルに追加しない） |
| synced | ローカルより updatedAt が新しい | リモートの内容で上書きする（削除済みなら、ローカルも削除済みになる） |
| synced | ローカルと updatedAt が同じか古い | 何もしない |
| pending | ローカルより updatedAt が新しい、または同じ | リモートの内容で上書きし、synced にする。そのデータのキューは捨てる（ローカルの変更は負け） |
| pending | ローカルより updatedAt が古い | 何もしない。ローカルの変更は、後の送信でリモートに反映する |

### フォルダの削除を取得したとき

- リモートからフォルダの削除を反映したとき、そのフォルダの配下（サブフォルダ・単語・成績）も、ローカルですべて削除済みにする。
  配下にこの端末だけで作った・変更したデータがあっても、削除済みにする。
- 配下を削除済みにした分はキューに積み、リモートにも削除を送る（リモートにしかない配下のデータも最終的に削除済みにそろえるため）。

## 送信（ローカル → リモート）

- キューに積んだ順に、1件ずつ送信する。
- 送信するときは、リモートの同じデータの updatedAt と比べる。比べてから書き込むまでの間に他の端末の書き込みが割り込まないようにする（Firestore ではトランザクションを使う）。

| リモートの状態 | 送信のしかた |
|--------------|------------|
| 存在しない | ローカルの内容を書き込む |
| ローカルより updatedAt が古い | ローカルの内容で上書きする |
| ローカルより updatedAt が新しい、または同じ | 書き込まない。リモートの内容でローカルを上書きし、synced にする（ローカルの変更は負け） |

- 1件の送信が終わったら、その項目をキューから消す。そのデータのキューが空になったら、ローカルの同期状態を synced にする。
  送信中にそのデータがまた変更された場合は、新しくキューに積まれた分が残るので、pending のままにする。
- 送信に失敗したら、そこで送信を止める。失敗した項目とそれ以降の項目は、順番を保ったままキューに残し、次のきっかけで先頭から再開する。
  これで、フォルダを作ってからその中に単語を作った、のような順番の依存が崩れない。
- 送信するのは、ログイン中のユーザーのキューだけ。他のユーザーのキューは送信しない。

## 同期のきっかけ

| きっかけ | 行うこと |
|---------|---------|
| ログインに成功したとき | 同期処理（取得 → 送信）。取得はすべてのデータを対象にする（そのユーザーの取得の基準がないため）。取得が終わるまでホーム画面に進まない。同期に失敗してもログインは成功のままにする |
| ログイン済みでアプリを起動したとき | 同期処理（取得 → 送信） |
| オフラインからオンラインに戻ったとき | 同期処理（取得 → 送信） |
| アプリがバックグラウンドから戻ったとき（resumed） | 前回の取得から5分以上たっていれば、同期処理（取得 → 送信）。5分未満なら何もしない |
| 登録・編集・削除をしたとき（オンライン） | 送信だけ（取得はしない） |

- どのきっかけでも、オフラインなら何もしない。
- 同期処理で取得に失敗したときは、送信もしない（取得してから送信する、という順番を守るため）。
- 同期処理・送信は同時に1つだけ動かす。動いている間に新しいきっかけがあった場合は、今の処理が終わってからもう1回だけ動かす（きっかけを取りこぼさず、同じ項目を二重に送らない）。
- 同期の失敗（通信エラー・認証エラーを含む）は画面に表示しない。強制ログアウトもしない。次のきっかけで再試行する。

## オンライン・オフラインの判定

- 端末がネットワークにつながっているか（`connectivity_plus`）で判定する。
- ネットワークにはつながっているがサーバーに届かない場合は、送信・取得が失敗するだけで、データは失われない（キューに残り、次のきっかけで再試行する）。
- リモートとの通信には時間の上限（タイムアウト）を設け、応答がない場合は失敗として扱う。

## ログアウト

- ログアウトするときは、オンラインなら先に送信を行う。
- ログアウトしても、そのユーザーのローカルのデータ・キュー・取得の基準は消さない。
  送信しきれなかった変更は、同じユーザーが次にログインしたときに送信する（オフラインで入力した内容をログアウトで失わないため）。
- 同じ端末で別のユーザーがログインしても、前のユーザーのデータは表示せず、送信もしない
  （読み取り・送信はログイン中のユーザーのデータだけを対象にし、キューには持ち主のユーザーを記録するため）。

## 登録・編集・削除の結果

| 結果 | 起きる条件 |
|-----|----------|
| 成功 | ローカルへの保存とキューへの登録が両方成功した（オンライン・オフラインに関係なく、送信の成否にも関係なく成功） |
| 失敗（`NotFoundFailure`） | 編集・削除の対象が存在しない、または削除済み |
| 失敗（`UnknownFailure`） | ローカルへの保存かキューへの登録が失敗した。この場合、どちらも保存しない |

- 登録・編集・削除では、通信エラー（`NetworkFailure`）・認証エラー（`AuthFailure`）は起きない（リモートと通信しないため）。

## フォルダの削除

- フォルダを削除すると、配下のサブフォルダ・単語・成績もすべて削除済みにする（カスケード削除）。
  フォルダと配下の削除は、1つのトランザクションで保存し、それぞれをキューに積む。

## 既存データの移行

- 今の SQLite（バージョン1）からの移行では、既存のデータを消さずに、新しい項目（deletedAt など）を追加する。
- 移行するとき、キューに変更が残っていないのに pending になっているデータは synced に直す。
- キューに残っている項目は、積んだ順番のまま引き継ぎ、対象データの持ち主のユーザーを記録する。
- 移行後の最初の取得は、すべてのデータを対象にする（新しい取得の基準がまだないため）。
