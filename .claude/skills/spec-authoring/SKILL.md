# 振る舞い仕様書の書き方（WordStock）

## 目的と大原則

振る舞い仕様書は、1つの機能（画面とその ViewModel・Repository）の**あるべき動作**を定義する文書である。
単体テスト・Widgetテストは、この仕様書を期待値の根拠にする。

仕様書は**対象の概要設計書**（人間が書く。下記「対象の概要設計書」）を正として作る。
`requirements.md`・`CLAUDE.md`・共通原則などは、概要設計書に書かれていない部分を補う補助として使う。

```
概要設計書（人間が書く・正） → 仕様書（Claude が作る・人間が承認） → テスト（仕様書を正とする）
```

作り方は対象によって次の2つに分かれる。

| 対象 | 作り方 |
|-----|-------|
| **新規機能**（仕様書を作る時点でコードがない） | 概要設計書を正とし、補助の文書・ユーザーの決定で補って作る。コードは根拠にしない |
| **既存機能**（仕様書を作る時点でコードがすでにある） | 上と同じ根拠から作る。上位の文書で決まらない振る舞いだけ、今のコードの動作を `現行追認` として書き、ユーザーの承認で確定する（下記「既存機能を仕様書にする場合」） |

**大原則: 今のコードの動作を、Claude の判断で仕様にしない。**

コードから期待値を作ると、バグもそのまま正解になり、テストがバグを検出できなくなる。
コードを読むのは「何を仕様として決める必要があるか（画面要素・操作・分岐）」を洗い出すためであり、
「どう動くべきか」は概要設計書から導き、概要設計書にないものだけ補助の文書・ユーザーの決定から導く。
**概要設計書と今のコードが食い違う場合は、概要設計書に従って書く**（コードに合わせない。テストが落ちてバグとして検出される）。
例外は既存機能の `現行追認` だけで、これもユーザーが承認するまで `確定` にしない。

## 作るもの

| ファイル | 内容 |
|---------|------|
| `docs/detailed_design/<置き場所>/<ファイル名>.md` | 1機能につき1ファイル。置き場所とファイル名は下記「置き場所とファイル名」に従う |
| 書式 | 末尾の「テンプレート」に従う。既存の仕様書は書式の手本にしない（古いルールで書かれている可能性があるため） |

1つの仕様書の範囲は「1画面 + その画面が使う ViewModel + Repository の契約」を基本とする。
複数画面で1つの ViewModel を共有している場合は、機能単位でまとめてよい。

### 置き場所とファイル名

詳細設計書は基本的に**画面が主体**になる。置き場所は、主体が画面かどうかで次の2通りに決める。

#### 1. 画面が主体の仕様書 → `lib/presentation/` と同じフォルダ階層・画面と同じファイル名

その画面（Page）が `lib/presentation/` のどのフォルダにあるかに合わせて、同じ階層に置く。
ファイル名は **Page のファイル名の拡張子を `.md` に変えたもの**にする（`sample_page.dart` → `sample_page.md`）。

| 画面 | lib/ の場所 | 仕様書の置き場所 |
|-----|-----------|----------------|
| サンプル画面 | `lib/presentation/sample/sample_page.dart` | `docs/detailed_design/presentation/sample/sample_page.md` |
| 単語作成画面 | `lib/presentation/word/word_create_page.dart` | `docs/detailed_design/presentation/word/word_create_page.md` |

仕様書が ViewModel・UseCase・Repository の契約を含む場合でも、置き場所は画面に合わせる
（domain / application / infrastructure の層ごとに分割しない）。

#### 2. 画面が主体でない仕様書 → `docs/detailed_design/` 直下に機能名のフォルダを作り、フォルダと同じファイル名にする

オフライン同期のように、特定の画面に属さない機能の仕様書は、`lib/` の構成には合わせず、
`docs/detailed_design/` の直下に**機能名のフォルダ**（snake_case）を新しく作り、その中に置く。
ファイル名は **フォルダ名と同じ名前**にする（`online_offline/` → `online_offline.md`）。

| 機能 | 仕様書の置き場所 |
|-----|----------------|
| オンライン・オフライン同期 | `docs/detailed_design/online_offline/online_offline.md` |

機能の仕様書が大きくなる場合は、同じ機能フォルダの中で複数ファイルに分けてよい。
その場合も、フォルダ名と同じ名前のファイル（`online_offline.md`）を入口として残し、分けたファイルは
その内容を表す snake_case の名前にする（例: `online_offline/sync_queue.md`、`online_offline/conflict_resolution.md`）。

#### 判断に迷う場合

- 画面の操作から始まる動作（ボタンを押す → 保存される 等）は、その画面の仕様書に書く
- 複数の画面から使われ、画面がなくても成り立つ動作（同期・競合解決 等）は、機能フォルダの仕様書に書き、
  画面の仕様書からは仕様 ID で参照する
- どちらか決められない場合は、確認で作業を止めず、2 のとおり `docs/detailed_design/` 直下に機能名のフォルダを作って置く。
  置き場所はユーザーがレビューで判断するので、手順6の報告で「置き場所を判断に迷った」ことと、その理由を伝える

## 根拠として読む文書（優先順）

| 優先 | 区分 | 文書 | 根拠欄の書き方 |
|-----|-----|------|--------------|
| 1 | **正** | **対象の概要設計書**（下記） | `概要 §<見出し>` |
| 2 | 補助 | ユーザーの決定（会話で決めたこと。概要設計書にない部分を埋める） | `ユーザー決定 YYYY-MM-DD` |
| 3 | 補助 | `CLAUDE.md`（エラーハンドリング・SQLite 同期ルール等） | `CLAUDE.md` |
| 4 | 補助 | `docs/high_level_design/online_offline.md`（同期・競合解決） | `online_offline §<節>` |
| 5 | 補助 | `docs/high_level_design/requirements.md`（アプリ全体の要件・エラーUI）※オフライン関連の記述は古い | `要件 §<節>` |
| 6 | 補助 | `docs/development/common_principles.md`（全画面共通の原則） | `原則-<番号>` |
| 7 | 補助 | 他機能の**承認済み**仕様書 | `<他の仕様ID>` |
| 8 | 補助 | 対象機能の今のコードの振る舞い（**既存機能のみ**。1〜7 で決まらない場合だけ） | `現行追認`（下記「既存機能を仕様書にする場合」） |
| — | — | 今のコードの画面文言・レイアウト（概要設計書に書かれていない場合だけ） | `現行UI`（使える範囲は下記） |

- 同じ事柄について、補助の文書が概要設計書と食い違う場合は**概要設計書に従う**
- ユーザーの決定が概要設計書と食い違う場合は、仕様書だけを直さず、ユーザーに概要設計書の修正を依頼する（正は概要設計書に置く）

### 対象の概要設計書

概要設計書は**人間が書く**。Claude は作成・修正しない（修正の提案はチャットで行う）。

| 対象 | 概要設計書の置き場所 |
|-----|------------------|
| 画面が主体の機能 | `docs/high_level_design/` 配下の、`lib/presentation/` と同じフォルダ階層に、`high_` + Page のファイル名（拡張子 `.md`）で置く。<br>例: `lib/presentation/sample/sample_page.dart` → `docs/high_level_design/presentation/sample/high_sample_page.md` |
| 画面が主体でない機能 | `docs/high_level_design/` 直下の機能名のファイル（例: `online_offline.md`） |

- **根拠欄の `§<見出し>`** には、概要設計書の見出しをそのまま書く（例: `概要 §ダイアログ`、`概要 §画面遷移`）
- **概要設計書が見つからない場合は、仕様書を作らずに止める**。ユーザーに概要設計書の作成を依頼する
- 概要設計書の書き方がわかりにくい・情報が足りない場合も、Claude が補って書き換えない。
  足りない点は `要確認` にし、手順6の報告で「概要設計書に追記してほしい点」として伝える

### `現行UI` を根拠にしてよい範囲

コードから採ってよいのは**見た目の定義**だけ:
画面タイトル・ラベル・ボタン名・メッセージの文言、画面要素の有無と配置、入力欄の制約値。

**振る舞い**（操作後に何が起きるか、失敗時の扱い、状態の変化、データの扱い）は `現行UI` を根拠にしない。
振る舞いが 1〜7 で決まらない場合は、新規機能なら `要確認` にしてユーザーに決めてもらう。
既存機能なら `現行追認` にする。

### 他機能に「準拠」する場合

他機能の**承認済み**仕様書の ID を根拠にする。仕様書がない他機能のコードには合わせない
（`現行追認` は対象機能自身のコードにだけ使う）。

### 既存機能を仕様書にする場合（`現行追認`）

**使ってよい条件**: 仕様書を作る時点で対象の Page・ViewModel がすでに `lib/` にあること。
新規機能では使わない。仕様書より後に書いたコードの動作も `現行追認` にしない。

**手順**:

1. 振る舞いごとに、まず根拠の 1〜7 で決まるかを確認する。決まるものはそちらを根拠にする
   （特に概要設計書とコードが食い違う場合は、概要設計書に従う）
2. 1〜7 で決まらない振る舞いは、今のコードの動作を書き、根拠を `現行追認`、確定度を `推測` にする
3. ただし、今のコードの動作が `CLAUDE.md` や `common_principles.md` に反している場合は `現行追認` にしない。
   あるべき動作を書いて確定度を `要確認` にし、手順6の報告で「バグの疑い」として伝える
4. 手順8でユーザーが仕様書を承認したら、ほかの `推測` と一緒に確定度を `確定` にする
   （根拠は `現行追認` のまま残す。概要設計書に追記されたときの見直し対象にするため）

**制約**: `現行追認` の項目から作るテストは、今の動作が変わったことを検出する回帰テストになる。
今のコードにすでにあるバグは検出できない。そのため、手順3の「バグの疑い」は追認に混ぜない。

## 確定度

| 確定度 | 付けてよい条件 |
|-------|--------------|
| `確定` | 根拠の文書に明記されている、ユーザーが決定した、または仕様書をユーザーが承認した（承認時に `推測` はすべて `確定` になる） |
| `推測` | 文書に明記はないが、原則や `現行追認` から妥当と判断した。承認までの一時的な状態で、`approved` の仕様書には残らない |
| `要確認` | 判断が分かれる、または推奨はあるが決めるのはユーザーであるべきもの。8章「要確認事項」に論点・案・推奨を必ず載せる |
| `廃止` | 使わなくなった項目。行は残し、理由を書く |

Claude が自分の判断だけで `確定` にしてはいけない。

## ID の付け方

形式: `<接頭辞>-<種別><2桁の連番>`（例: `WRC-C03`）

- **接頭辞**: 機能ごとに 3 文字の英大文字。仕様書の先頭（frontmatter の `prefix`）で宣言し、
  既存の仕様書と重複させない（`docs/detailed_design/` 配下をサブフォルダまで確認する）
- **種別**:

| 種別 | 意味 |
|-----|------|
| N | データ定義・入力ルール |
| D | 表示（初期表示・読み込み・一覧・空表示） |
| C | 作成 |
| U | 更新・変更 |
| X | 削除 |
| E | エラー種別ごとの扱い |
| V | ViewModel の状態 |
| R | Repository の契約 |

CRUD に当てはまらない操作（ログイン、テスト回答、設定切り替え等）は、仕様書の frontmatter の `kinds` で
種別の文字を追加宣言する（例: `L: ログイン操作`、`A: 回答操作`）。上の表の文字と重複させない。

- **ID は振り直さない・使い回さない**。テスト項目書が ID を引用するため。
  項目を削除するときは行を残し、確定度を `廃止` にして理由を書く。追加は末尾の連番で行う

## 仕様項目の洗い出し方

漏れを防ぐため、次の順で洗い出す。

1. **画面要素の一覧**: 表示される要素・ボタン・メニュー・ダイアログ・入力欄をすべて挙げる
   （既存機能はコードから、新規機能は概要設計書から）
2. **状態の一覧**: 読み込み中 / データあり / 0件 / 初期読み込み失敗 / 処理中 など、画面が取りうる状態
3. **操作 × 結果の組み合わせ**: 各操作について、次の結果をすべて検討する

| 観点 | 例 |
|-----|----|
| 成功 | 作成に成功 → 一覧の末尾に追加 |
| 失敗 | 発生しうる Failure ごと（`NotFoundFailure` / `UnknownFailure` / `NetworkFailure` / `AuthFailure`） |
| 入力の境界 | 空・空白のみ・上限ちょうど・上限超過 |
| 中断 | キャンセル・戻る |
| 処理中 | 連続タップ・処理中の他操作 |
| 対象の不在 | 変更・削除の対象が既に存在しない |

4. **共通原則との突き合わせ**: `common_principles.md` の各原則が、各操作に当てはまるかを確認する
5. **状態が多い画面**（例: テスト回答画面）は、状態遷移表（現在の状態 × 操作 → 次の状態）を追加する

## 書き方のルール

仕様書の主な読み手は、テストを書く Claude である。**1 行をそのままテストケース 1 件に変換できる**ことを最優先にする。
人間にとっての読みやすさより、曖昧さがないことを優先する。

### 1 ID = 1 テストケース

- 1 つの ID には、1 つの条件と、その条件での結果だけを書く
- 次の書き方は禁止。行を分ける

| 禁止 | 例 | 直し方 |
|-----|----|-------|
| 結果の中に分岐がある | 「成功なら一覧、失敗なら `AsyncError`」「成功すれば〜」 | 成功の行と失敗の行に分ける |
| 複数の操作をまとめる | 「作成・変更・削除に成功」 | 作成・変更・削除でそれぞれ 1 行 |
| 他の行を参照して中身を省く | 「SMP-C02〜C05 と同じ」 | 同じ内容でも行ごとに書き直す（根拠欄で元の ID を引用してよい） |
| 条件が話題になっている | 「一覧の並び順」「変更後の日時」「入力欄の制約」 | 「作成日時の異なる3件がある状態で画面を開いた」のように状態と操作で書く |
| 複数の対象に同じルールを1行で当てはめる | 「作成ダイアログ・編集ダイアログの入力欄の両方に適用する」 | 対象（画面・ダイアログ・入力欄・メソッド）ごとに ID を分ける。内容が同じでも行を書き直す（根拠欄で元の ID を引用してよい）。ID の引用だけでは、片方の対象のテスト漏れを検出できないため |

- 同じ条件での結果が複数あるのはよい（例: ダイアログのタイトル・ラベル・ボタン名を 1 行で書く）。1 つのテストで複数の `expect` にする
- **例外: 2.2 入力ルール**の ID は、境界値の数だけテストケースになる（有効・無効の値ごとに 1 件）

### 条件には前提をすべて書く

テストの準備（Arrange）を仕様書だけで組めるようにする。

- **既存データ**: 件数と中身（例: 「『A』『B』の2件がある状態で」）
- **失敗させるとき**: どの Failure で失敗するか（例: 「作成が `UnknownFailure` で失敗した」）。
  「失敗した」だけにしない。Failure の種類で動作が変わらない場合は、代表の 1 種類（通常は `UnknownFailure`）を書き、
  **代表以外**の Failure を 3.n のエラー種別の表に書く。代表の Failure を 3.n に重ねて書かない
- **操作**: 何をどの順で行ったか

### 期待される動作は、テストで観測できる結果で書く

- 「正しく表示される」「適切に処理される」「問題なく」は禁止
- 「〜が行われる」「通知される」「実装に委ねる」のように、何を確かめればよいか決まらない書き方も禁止。
  次の表の観測点のどれかで書く

| 章 | 観測点（書いてよいもの） |
|---|---|
| 3章 画面 | 表示される文言（「」で囲む）、要素の表示・非表示、ボタンの有効・無効、一覧の中身と順序、ダイアログ・スナックバー・`ErrorScreen` の表示、遷移先のパス |
| 4章 ViewModel | State の項目名とその値（`AsyncData([A, B])` / `AsyncError(UnknownFailure)` 等）、Repository が呼ばれた回数と引数 |
| 5章 Repository | 戻り値（`Right(...)` / `Left(NotFoundFailure)`）、その後の取得メソッドの戻り値 |

- **時刻**は具体的な値で書かない（テストで固定できないため）。前後関係で書く
  （例: 「updatedAt が変更前の updatedAt より後になる」「createdAt と updatedAt が等しい」）
- **「〜が起きない」**も観測点で書く（例: 「Repository の createSample が1回だけ呼ばれる」「一覧が2件のまま」）
- 観測できる層が画面だけのもの（スナックバー等）は 3章にだけ書く。
  4章では、その画面表示の元になる State の値を書く。State で表せない場合は `要確認` にする

### 入力ルールは、具体的な値と守る層まで書く

2.2 入力ルールの各行には、次を書く。

- **守る層**: そのルールを守らせる層（`画面` / `ViewModel` / `UseCase` / `Repository`）。
  それより下の層に違反した値が渡された場合の動作も書く。扱わない場合は「下の層には渡されない前提（テスト対象外）」と書く
- **境界値**: テストにそのまま使える具体的な値を、有効と無効に分けて書く。文字数・桁数の制限なら次を必ず含める
  - 上限ちょうど（有効）、上限＋1（無効）
  - 空、空白のみ（半角・全角スペース）
  - 文字種で数え方が変わる場合は、それぞれの文字種と混在
- **加工の順序**: 空白の除去と上限の判定のように、加工と判定がある場合はどちらが先か

### 4章は 3章と対応させる

- 3章の行のうち、**ViewModel の状態が変わるもの**（一覧の中身・読み込み状態・失敗時の状態）は、
  4章に対応する V の行を作り、「対応する画面仕様」列にその ID を書く
- **画面だけで完結するもの**（ダイアログの開閉・ボタンの有効無効・文言）は 4章に書かない。Widget テストだけで検証する
- こうすることで、Widget テストと単体テストで同じ仕様を二重に検証しない

### その他

- **文言は正確に書く**。テストが `find.text()` で検索できるように「」で囲む
- **実装方法は書かない**（メソッドの中身・private なメソッド名・Widget の組み方）。
  例外として、上の観測点の表にあるもの（観測する型、4章の State の項目名、Repository のメソッド名）は書いてよい
- **条件は重ならないようにする**。同じ条件で2つの ID が違う動作を定めないようにする
- **テストしない項目**（「発生しない」「対象外」等）は ID を作らず、7章「対象外」に理由と一緒に書く
- ユースケースが Repository への委譲だけなら、6章は「委譲のみ。仕様項目なし」と書き、項目を作らない

## 仕様書に書いてはいけないこと

- **今のコードとの差異**（「現在の実装では〜になっている」等）。
  テストを書く側が差異を知ると、仕様からではなく差異から期待値を作ってしまう。
  差異はユーザーへの報告（手順6）でだけ伝える
- **バグの存在や修正方法**
- **テスト手順**（pump の回数・Fake の組み方など、どう検証するかはテスト項目書とテストコードの役割）。
  何を観測すればよいか（上の「観測点」）は書く

## 作業手順

1. **対象の確定**: 対象の機能が**新規機能**か**既存機能**か（対象の Page・ViewModel がすでに `lib/` にあるか）を判定する。
   既存機能なら、関連するファイル（Page / ViewModel / State / UseCase / Repository interface / Mock）を特定する。
   置き場所とファイル名（上記「置き場所とファイル名」）と接頭辞を決め、`docs/detailed_design/` 配下の既存仕様書と接頭辞が重複しないことを確認する
2. **根拠を読む**: まず**対象の概要設計書**を読む（見つからなければ止めてユーザーに作成を依頼する）。
   次に補助の文書を読む。`common_principles.md` は必ず読む
3. **コードを読む**（既存機能のみ）: 洗い出しの手順1〜2のため。振る舞いは 1〜7 で決まらないものだけ `現行追認` にする。
   新規機能はこの手順を飛ばし、画面要素・状態は概要設計書から洗い出す。概要設計書で足りない部分は `要確認` にする
4. **下書き**: 末尾の「テンプレート」の章立てで書く。該当しない章は削除せず「該当なし」と書く。
   frontmatter の `status` は `draft`
5. **自己レビュー**: 下の「チェックリスト」をすべて確認する
6. **ユーザーへの報告**（チャットで。仕様書には書かない）:
   - 作成したファイル
   - 要確認事項（論点・案・推奨）
   - 概要設計書に追記してほしい点（概要設計書に書かれておらず `要確認` や `現行追認` になった項目）
   - コードが仕様と食い違っていそうな箇所（ID と、今のコードの動作）。既存機能では「バグの疑い」として伝える
   - 確定度が `推測` の項目の一覧（既存機能では `現行追認` の項目とそれ以外を分けて示す）。
     承認すると `推測` はすべて `確定` になるので、否定したい項目があれば承認前に指摘してほしいと伝える
7. **決定の反映**: ユーザーが決めた項目は、確定度を `確定`、根拠を `ユーザー決定 YYYY-MM-DD` にする。
   8章の該当行は削除せず「決定: 案A（YYYY-MM-DD）」と記録する
8. **承認**: 要確認が 0 件になり、ユーザーが承認したら `status: approved` にし、`推測` の項目をすべて `確定` にする。
   **ユーザーの明示的な承認なしに `approved` にしない**

### 承認後の改訂

- 仕様を変えるときは `status` を `draft` に戻し、手順6〜8をやり直す
- 変更した ID は同じ ID のまま内容を更新する。意味が大きく変わる場合は旧 ID を `廃止` にして新しい ID を追加する
- frontmatter の `updated` を更新する

- [ ] 入力がある操作に「空」「上限ちょうど」「上限超過」の仕様がある
- [ ] 変更・削除に「対象が存在しない」場合の仕様がある

- [ ] 概要設計書と食い違う項目がない（補助の文書・`現行UI`・`現行追認` で上書きしていない）

- [ ] frontmatter（`feature` / `prefix` / `status` / `targets` / `updated`）がある
- [ ] 1 つの ID に、結果の分岐（成功なら〜失敗なら〜）・複数の操作・他の行への参照による省略がない

- [ ] 画面に表示される文言が「」で正確に書かれている

## テスト工程との関係

- テスト項目書（`test/test_cases/**/*_test_cases.md`）の各ケースは、期待結果の根拠として仕様 ID を引用する
- **仕様 ID とテストケースの対応**:
  - 3章・5章の ID → 1 件以上の Widget テスト／Repository の単体テストから引用される
  - 4章の ID → 1 件以上の ViewModel の単体テストから引用される
  - 2.2 の ID → 「守る層」のテストから、境界値の有効・無効それぞれ 1 件以上引用される
  - `廃止` の ID は引用しない
- テストの期待値は `status: approved` の仕様書からのみ取る
- テストが仕様どおりの期待値で落ちた場合は、プロダクションコードのバグとして扱う（期待値をコードに合わせない）
